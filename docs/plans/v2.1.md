**Status:** proposed, 2026-11-11. Nothing here is decided until the maintainer answers §7.

## 2. Goals and non-goals

Goals: every user gets the fixes already merged; no gate fails open; `/arena` lets competing
proposals fight while tests decide what tests can decide; round 4 measures it before the README
claims anything.

Not in 2.1: new always-on rules; `/arena` on hosts other than Claude Code; spending the user did not
start; Windows parity beyond #45's listed gaps.

**The lazier alternative** to `/arena` is asking again, or `/plan` and `/review` as they are. It
earns its place only if round 4 shows a gain on hard tasks worth its cost. If it does not, it stays
experimental or goes.

### M2: `/arena`

#### What upstream is

`Jakeschincariol/arena-skill` at `df07b8e` (one commit; MIT, © 2026 Jake Schincariol): `SKILL.md`
(the orchestration and five prompt templates), `bracket.py` (1,235 lines, Python 3.8+ standard library
only), `strategies.json` (15 reasoning modes × 12 workflows × 12 strategies = 2,160 cards), `rubric.md`
(five weighted criteria) and 404 lines of unittests. N subagents get the same task and different
cards, then fight a single-elimination bracket: attack, defend and revise, judge. A run costs 6N − 5
subagent calls, plus one when there is a rejected answer to beat: 43 for 8 agents, 91 for 16, 595 for
the default 100. Every agent writes to `.arena/` and replies in one line, and the state is one JSON
file, so a run survives compaction.

#### Measured: upstream reviewing this plan

On 2026-11-11 upstream's skill, as installed, ran on this plan ("review this plan") with its defaults:
100 agents, waves of 10, `general-purpose` subagents on the session's model. At the user's choice it
stopped after the first wave, so this measures ten competitors' spawn calls; attack, defend and judge
calls went unmeasured.

| Per competitor                       | Mean        | Range           |
| ------------------------------------ | ----------- | --------------- |
| Tokens, as the session reported them | 374,692     | 247,511–485,391 |
| Tool calls                           | 91          | 47–117          |
| Wall time                            | 30 minutes  | 20–42 minutes   |
| Solution length (`wc -w`)            | 3,965 words | 1,465–6,234     |

The wave took 42 minutes, as long as its slowest member, and 3.75M tokens in all; the session does not
break out cached input, so that is not a bill. Eight of the ten wrote to their scratch folders, one a
full copy of `.claude/` with generated test inputs, another 543 files and 60 MB; the two that wrote
nothing there were the cheapest, at 247,511 and 278,727 tokens. Each competitor also loaded this
repository's always-on rules, as subagents do in a checkout that carries `.claude/rules/`.

What it changes:

- **Cost is tokens and hours, not calls.** At the first wave's rate, upstream's 100-agent default
  spends about 37M tokens on its spawn alone, and its 70 waves take about two days. The 8-agent default
  here spends about 3M on its spawn, in one wave. `plan` prints an estimated token and time range, from
  measured runs, before the spawn (M2.6).
- **Tool use drives the cost**, which backs taking Bash from arena agents and letting the gate run code
  instead. R12 asks how to cap one agent's turns or tokens.
- **A wave waits for its slowest member**, 42 minutes against a mean of 30 (R3).
- **Round 4's arena arm cannot run within round 3's limits**: the measured wave alone overran the
  bench's 1,500-second timeout (M3).

#### Why it fits

It already keeps several of Nonna's principles. The bookkeeping is code; the orchestrator never
judges; `bracket.py` does the arithmetic and enforces the fatal rule; every random choice is seeded
and the seed recorded; the main context holds receipts, not solutions; the winner is a proposal it
never applies. An arena is a search of the solution space, which
[ADR-0002](../adr/0002-llm-proposes-gates-decide.md) allows upstream of the gates, provided its output
still passes them.

#### Gated mode: the referee includes the suite

For a code task where a test command is recorded (`nonna.testCmd`, or a directory's own,
[ADR-0014](../adr/0014-a-test-command-per-directory.md)):

1. **The base is the working tree the agents read**, not `HEAD`: a snapshot of tracked changes and
   untracked files, taken before the spawn, so a diff written against a dirty tree applies.
2. **Per-test results, read by machine.** The gate compares per-test outcomes from a machine-readable
   report (JUnit XML, or the runner's own result file; R11), its totals checked. No such report, a
   truncated one or a partial parse counts as unreadable, and then the whole suite must be green.
   `lib/tests.sh`'s failure digest is for display only: it keeps five lines.
3. **A baseline in the same sandbox.** The suite runs once on the base inside the same sandbox and
   kind of scratch clone as the candidates. A red baseline is the normal case for a bug fix, and the
   gate judges candidates against it. The base also runs once outside the sandbox, the way Stop runs
   the user's own code; if the sandboxed baseline fails a test the other passes, the suite needs
   something the sandbox withholds, so gated mode turns off. A suite that cannot run at all does the
   same.
4. **One gate job per revised solution a judge will read**: 2N − 2 runs plus the two baseline runs,
   16 for 8 agents (one more when the rejected answer to beat carries a diff). Each job is its own Bash
   call with a 600-second timeout, and the suite inside it gets 540, leaving room for the clone, the
   snapshot and the sandbox. A job writes a start marker first; a start marker with no result once its
   call has returned is a failed gate, so a killed job ends its match instead of stalling it.
5. **Isolation.** Each job copies the base into a scratch tree outside the repository: a separate
   clone with its own `.git`, never a linked worktree, whose `.git` leads back to the user's. The
   ignored directories the suite needs (`node_modules`, `.venv`, build output) are made available
   read-only. The job applies the diff and runs the command(s) `lib/tests.sh` would choose inside an
   OS sandbox: no network, an `env -i` allowlist, writes only to the scratch tree. A service or a
   variable the suite needs gets in only through an allowlist the user approves (R10). Where no
   sandbox is available (R8), gated mode is off. As defence in depth, the job hashes `.git/hooks`,
   `.git/config`, `.git/nonna-green` and `.git/nonna/` (but not `nonna/arena/`) before and after,
   writes its result only after the second hash, and halts the run on any change. The scratch tree is
   removed when the job ends, and the run removes whatever is left.
6. **Fail-closed verdicts.** A candidate passes when no test that passed on the base fails and every
   test named with `--must-pass` passes. Those names are a structured argument the user gives
   `/arena`, checked against the baseline's test list and printed by `plan`, which waits for the user's yes, before the spawn; they are
   never read from the task file the model writes. Everything else fails: a diff that does not apply,
   a timeout (unlike Stop, where out of time is not red), a killed job, a crash of the gate itself, an
   unreadable result, a secret pattern in the added lines. The judge phase does not start for a match
   whose gate result is missing.
7. **The decision.** `decide()` reads the result: fatal = the judge's fatal, or a failed gate. The
   judge sees the digest, scores what tests cannot see (requirements, design, clarity), and is told
   the suite's verdict is final. When every candidate failed, the report's first line says no
   candidate passed the suite.
8. With no test command, no sandbox, or a baseline the sandbox changes, the run is rubric-only, and
   the result's first line says so and why.

The winner is still a proposal. `/arena` ends by offering `/tdd` to land it test-first, or `/review`
of its diff, and never applies anything itself.

### M3: round 4, measure it

`plugin-lite+arena` (8 agents, gated where the suite allows); and a compute-matched control, `plugin-lite` given the arena

Gated mode runs only on suites whose sandboxed baseline matches the unsandboxed one. The real suite needs PostgreSQL and settings in the environment, so the preregistration, frozen before any paid run, names its arena arm gated only if R10 has landed by then, and rubric-only otherwise; the README claims only the mode that was measured. Record the unsafe
rate, pass rate, cost multiple, wall time and gate firings. The preregistered rule: the README claims a
gain only if the real suite's pass rate beats both other arms, the unsafe rate does not rise, and the
cost per passing change stays under a ceiling fixed in the preregistration. Add the two runs STATUS
already wants: a task whose suite cannot be made green (the test gate's escape), and a Codex arm.
